# Songyuan OS3.0.301.0.WGNTWXM stock evidence

The source is the user's `songyuan_tw_global_images_OS3.0.301.0.WGNTWXM_20260804.0000.00_16.0_tw_0af1964e16` fastboot ROM. Its `boot.img` SHA256 is `8d58da2115d1343e08d870f481707de9905e3d6a4e7900e3f16a1c00d7f479f1`, matching `stock/boot.img.gz` after decompression. The stock `vbmeta.img` SHA256 is `e343afe819994efe23db759f8980664915b08dde6b774c7ae396be8a8309be35`. `avbtool verify_image` verified both stock images' embedded RSA4096 signatures when OpenSSL was available. `vbmeta.img` chains `boot` at rollback index location 3.

The `IKCFG_ST` / `IKCFG_ED` payload embedded in that stock boot decompresses to SHA256 `76d553a0b591daefa8912036c772b8ff86e2371e661250cf0eaf56c5726837d4`. This exact configuration replaces the modified repo copy. The old copy had disabled `CONFIG_MODULE_SIG_PROTECT` and `CONFIG_TRIM_UNUSED_KSYMS`, while the stock kernel enables both and names `protected_module_names_list` and `abi_symbollist.raw` as build inputs.

The ROM's sparse `super.img` contains EROFS `vendor_dlkm_a` and `system_dlkm_a`. The CRC reference was regenerated from the `__version_ext_names` and `__version_ext_crcs` sections of 398 vendor and 206 system modules. Exports found in those modules were excluded from the kernel symbol reference; their import CRCs were checked against the corresponding module providers. The resulting reference has 3,809 kernel symbol names, no malformed CRCs, no conflicts, and no module-to-module CRC mismatches. Reproduce it with `tools/vendor_crc_from_modules.py` after extracting those two partitions and installing `pyelftools`.

All 398 vendor modules report `6.12.69-android16-6-maybe-dirty-4k` in `vermagic`; all 206 system modules report `6.12.69-android16-6-g0d80ee00f747-ab15461283-4k`. This is stock ROM evidence and must not be treated as a final-kernel failure by itself. The compiled final kernel still requires an exact release and CRC comparison. No final kernel was built or boot-tested during this audit.

The stock boot has a signed OEM AVB footer. The repository's `gki_testkey.pem` is not the OEM key, so the current repacker refuses to mark a modified boot image flashable. A verified signing or explicitly unverified debug-boot procedure remains necessary before device testing.

The older `boot-sukisu-ultra-songyuan-4k.img` has its OEM AVB metadata immediately after the padded kernel. The stock boot has an additional 16,384-byte GKI signature region at that position containing two RSA4096 VBMeta records (`boot` and `generic_kernel`). The old artifact omitted this region and also used `Algorithm: NONE` for its OEM AVB footer. These are concrete boot-structure differences in addition to its mismatched `-dirty` kernel release.

The [2026-09-23 Kleaf build](https://github.com/ldductruonggiang/songyuan-kernel-builder/actions/runs/35827720750) reached compilation but failed in pinned SukiSU commit `b20dee702035af09cb2ecb5f35443bbc1747f3e6`: `netlink_kernel_cfg.cb_mutex` is absent from ACK 6.12 and `security_add_hooks()` requires `const struct lsm_id *` instead of a string. The upstream [Linux 6.12 issue](https://github.com/SukiSU-Ultra/SukiSU-Ultra/issues/921) remains open, and the `builtin` branch still points to that commit as checked on 2026-09-23. The project owner explicitly forbids a custom SukiSU compatibility patch, so the workflow now fails with this precise blocker until an official compatible upstream commit can be pinned. No flashable final image has been produced.
